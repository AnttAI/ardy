# ARDY Newton RTX Viewer

`viewer_process.py` launches the ARDY/T3 Newton viewer. It can show the T3 robot, receive live frames over WebSocket, render with Newton `ViewerGL` or `ViewerRTX`, and run the interactive pick-table bottle physics scene.

The built-in **Play T3 Demo Pick** motion is generated locally with Newton IK. It is not generated by SOMA retargeter and it is not generated by a learned model.


For RTX rendering, Newton must be installed with its RTX viewer dependencies.

## Launch command

Recommended command using the repo background asset:

```bash

python newton_rtx_viewer/viewer_process.py \
  --viewer rtx \
  --background-usd newton_rtx_viewer/assets/robot-ovrtx.usda \
  --pick-table-physics \
  --websocket-server \
  --websocket-host 0.0.0.0 \
  --websocket-port 8765 \
  --camera-preset saved_front \
  --playback-mode realtime \
  --rtx-environment studio \
  --pick-table-physics-backend mujoco-cpu \
  --physics-substeps 8 \
  --debug-pick-fps 10 \
  --debug-pick-physics-substeps 2 \
  --ovstream-webrtc \
  --ovstream-port 49104
```

Your older command also works, but MuJoCo bottle physics now internally forces smoother settings for the demo pick:

```text
physics substeps: at least 16
T3 demo pick FPS: at least 60 for MuJoCo
```

If you use `--viewer gl`, remove the ovstream flags because WebRTC streaming needs RTX render products.

## What the main flags do

| Flag | Purpose |
|---|---|
| `--viewer rtx` | Uses Newton RTX rendering. Required for ovstream WebRTC output. |
| `--background-usd ...` | Loads the visual background scene. Use the repo `assets/robot-ovrtx.usda` path for portability. |
| `--pick-table-physics` | Adds dynamic bottles and hidden table colliders. |
| `--pick-table-physics-backend mujoco-cpu` | Uses MuJoCo CPU physics for the bottles. This is the realistic pick path. |
| `--physics-substeps 16` | Runs smaller physics steps for stable contact/friction. |
| `--websocket-server` | Starts a WebSocket receiver for live ARDY/SOMA/T3 frames. |
| `--playback-mode realtime` | Uses the newest available frame and drops stale queued frames. |
| `--ovstream-webrtc` | Streams RTX render output to a browser/client. |

## How bottle pick motion is generated

The built-in pick motion starts when you press **Play T3 Demo Pick** in the UI or send a WebSocket command such as `play_t3_demo_pick`.

The code path is:

```text
Play T3 Demo Pick
  -> start_t3_demo_pick_playback(...)
  -> read selected bottle live pose from Newton state
  -> compute staged robot root x/y/yaw
  -> _make_t3_demo_pick_frames(...)
  -> Newton IK solves right-arm waypoints
  -> generated t3_row frames are played by _apply_t3_row(...)
  -> MuJoCo advances bottle/table/gripper contacts
```

Important functions:

```text
start_t3_demo_pick_playback       chooses the selected bottle and computes robot root staging
_make_t3_demo_pick_frames         generates the IK motion frames
_apply_t3_row                     applies each robot root/joint row to the viewer state
_add_interactive_bottles          creates dynamic bottle bodies
_add_visible_t3_gripper_rubber_pads creates the right/left visual rubber pads
_configure_mujoco_pick_contacts   sets MuJoCo contact dimension for bottle/gripper contact
```

## How it adapts to different bottle positions

The viewer reads the selected bottle's current physics position:

```python
target_bottle_pos = state.body_q.numpy()[bottle_body_indices[selected_bottle_index], :3].copy()
```

Then it maps that world position into a fixed local arm workspace:

```python
desired_local_target = [0.50, -0.28, bottle_z]
```

The robot root is then translated and yawed so that this fixed local target lines up with the real selected bottle:

```text
job_yaw = atan2(target_y, target_x) - atan2(-0.28, 0.50)
```

This means the right-arm IK motion is mostly the same for different bottles, while the robot base/root pose changes to aim the motion at the selected bottle.

If the bottle is too far for the staged IK target, the motion generator stops with:

```text
Selected bottle or lift target is out of reach from the current base; select a closer bottle
```

## Pick trajectory

The generated trajectory follows the same phase structure as the reference `/home/jony/Downloads/t3_pick_place/example.py` demo:

| Time | Phase | Target |
|---:|---|---|
| 0-1 s | settle | home |
| 1-2 s | wait/open | home |
| 2-3 s | reach | bottle grasp point |
| 3-4 s | grasp | close gripper around bottle |
| 4-6 s | lift | bottle position + 0.28 m Z |
| 6-8 s | transfer | move above place point |
| 8-9 s | lower | place point |
| 9-11 s | release | open gripper |
| 11-15 s | retract | move back home |

The waypoint positions are built like this:

```python
home        = grasp_point - [0.15, 0.0, 0.0]
lift        = grasp_point + [0.0, 0.0, 0.28]
place_point = grasp_point + [0.0, 0.34, 0.0]
above_place = place_point + [0.0, 0.0, 0.30]
```

The wrist IK target uses `right_gripper_base` with this local offset:

```python
grip_offset = [0.0, 0.0, 0.11]
```

The wrist rotation target is approximately a 90 degree Y-axis rotation:

```python
quat = [0.0, sqrt(0.5), 0.0, sqrt(0.5)]
```

## Gripper and bottle physics

The bottle is a dynamic MuJoCo body. The code does not attach the bottle to the hand and does not manually move it during the pick. The bottle should move only because MuJoCo resolves contact, friction, mass, and gravity.

Current bottle constants:

```text
radius:      0.028 m
half height: 0.090 m
mass target: 0.115 kg
```

Current gripper constants:

```text
open aperture:  0.095 m
closed aperture: 0.000 m
grip aperture minimum around bottle: 0.044 m
rubber friction: 1.2
rubber pad half extents: (0.022, 0.030, 0.002)
rubber pad local offset: (0.0, -0.032, 0.0)
```

The right visible rubber pads are kept as the MuJoCo contact geometry. Other T3 collision shapes are disabled in the default pick-table mode to keep the contact problem small and stable.

## Moving bottles in the UI

The UI lets you select a bottle and adjust X/Y/Z. Moving a slider calls `_move_interactive_bottle(...)`, which updates:

```text
state.body_q
state_next.body_q
model.joint_q free-joint coordinates
```

Pressing **Play T3 Demo Pick** should not reset moved bottles. Bottles reset only when you press **Reset Bottles**.

## Logs to watch

During runtime, watch these fields:

```text
physics_backend=mujoco-cpu
substeps=16/16
grip_contacts=<number>
physics_ms=<time>
```

Expected behavior:

```text
physics_backend should be mujoco-cpu
grip_contacts should become > 0 when the right gripper touches the selected bottle
```

If `grip_contacts` stays `0`, the hand is not physically contacting the selected bottle in MuJoCo.

If `physics_backend` says XPBD or fallback, MuJoCo did not start correctly.

## Notes about SOMA

SOMA retargeting is separate from the built-in T3 bottle-pick demo.

SOMA payloads can provide human mesh/skeleton data for visualization and retarget display, but **Play T3 Demo Pick** uses local Newton IK from the bottle position. It does not need a SOMA mesh payload to generate the T3 pick motion.
